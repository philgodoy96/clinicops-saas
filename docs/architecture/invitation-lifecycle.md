# Invitation Lifecycle

## Purpose

ClinicOps uses invitations as the controlled onboarding boundary for tenant memberships.

A global user does not gain tenant access merely by existing in the platform. A tenant membership is created only through an explicit onboarding workflow that validates:

- the target tenant;
- the invited email;
- the initial tenant role;
- the invitation issuer;
- the invitation lifecycle state;
- token validity;
- user lifecycle state;
- existing membership state;
- transactional consistency.

This prevents generic membership creation from bypassing tenant authorization, invitation expiration, replay protection, or disabled membership policies.

## Ownership Boundaries

The invitations module owns:

- invitation persistence;
- invitation lifecycle state;
- invitation token generation and digesting;
- invitation issuance;
- invitation expiration checks;
- invitation revocation;
- invitation acceptance;
- membership onboarding through accepted invitations;
- invitation-specific concurrency handling.

The invitations module depends on:

```text
identity
    -> canonical email policy
    -> global user lookup
    -> global user creation
    -> password credential creation
    -> user lifecycle state

tenancy
    -> tenant persistence
    -> membership persistence
    -> tenant roles
    -> tenant lifecycle state
    -> membership lifecycle state
    -> tenant-scoped locking
```

The invitations module does not own:

- authentication sessions;
- access or refresh tokens;
- email delivery;
- email templates;
- tenant permission evaluation;
- membership role changes after onboarding;
- membership reactivation;
- ownership transfer;
- audit log persistence;
- background cleanup jobs.

## Invitation Model

The `invitations` table stores one tenant-scoped onboarding request.

Fields:

```text
id
tenant_id
invited_email
role
status
token_digest
created_by_membership_id
accepted_by_user_id
expires_at
accepted_at
revoked_at
created_at
updated_at
```

Properties:

- `id` is a UUID;
- `tenant_id` identifies the target tenant;
- `invited_email` is stored in canonical form;
- `role` defines the membership role created after acceptance;
- `status` stores the invitation lifecycle state;
- `token_digest` stores only the SHA-256 digest of the bearer token;
- `created_by_membership_id` identifies the tenant membership that issued the invitation;
- `accepted_by_user_id` is populated only after successful acceptance;
- invitation timestamps are timezone-aware.

The issuing actor is represented by a membership rather than only a global user because invitation authority exists within a tenant context.

## Lifecycle States

Persisted states:

```text
pending
accepted
revoked
expired
```

### Pending

A pending invitation may be accepted only before its `expires_at` timestamp.

### Accepted

An accepted invitation created one membership and cannot be used again.

An accepted invitation requires:

```text
accepted_by_user_id
accepted_at
```

and must not contain:

```text
revoked_at
```

### Revoked

A revoked invitation was explicitly invalidated by an authorized tenant actor.

A revoked invitation requires:

```text
revoked_at
```

and must not contain acceptance state.

### Expired

An expired invitation is no longer valid because its validity window ended.

Expiration has two representations:

```text
Persisted expiration
    -> status = expired

Effective expiration
    -> current_time >= expires_at
```

A pending invitation whose timestamp has elapsed is rejected even if a background process has not yet materialized the `expired` status.

## Role Restrictions

Invitations may grant:

```text
admin
staff
```

Invitations may never grant:

```text
owner
```

The application validates this before persistence.

PostgreSQL also enforces:

```sql
CHECK role <> 'owner'
```

Constraint name:

```text
ck_invitations_role_not_owner
```

Tenant ownership remains assignable only through the dedicated ownership transfer workflow.

## Token Security

Invitation tokens are bearer secrets.

Generation uses:

```text
32 cryptographically random bytes
        |
        v
URL-safe encoding
```

The plaintext token is returned once by the issuance service for a future delivery layer.

The database stores only:

```text
SHA-256(plaintext token)
```

The plaintext token is never persisted.

### Why SHA-256 Is Appropriate

Passwords have low human-generated entropy and require a deliberately expensive password hashing algorithm such as Argon2id.

Invitation tokens are generated by the system with high entropy.

```text
Human password
    -> Argon2id

Random invitation bearer token
    -> SHA-256 digest
```

The digest supports indexed lookup without storing the bearer secret.

### Representation Safety

Token-bearing application objects hide sensitive fields from their default representations:

```text
InvitationToken
    -> plaintext excluded from repr
    -> digest excluded from repr

AcceptInvitationCommand
    -> token excluded from repr
    -> password excluded from repr

IssuedInvitation
    -> token excluded from repr
```

This reduces accidental exposure through diagnostic logging.

It does not replace the requirement that application logs avoid serializing secrets explicitly.

## Persistence Invariants

### Globally Unique Token Digest

The database enforces:

```text
UNIQUE (token_digest)
```

Constraint name:

```text
uq_invitations_token_digest
```

### One Pending Invitation per Tenant and Email

The database enforces a partial unique index equivalent to:

```sql
UNIQUE (tenant_id, invited_email)
WHERE status = 'pending'
```

Index name:

```text
uq_invitations_one_pending_per_tenant_email
```

Terminal invitations do not prevent future issuance for the same tenant and email.

### Expiration Ordering

The database enforces:

```sql
CHECK expires_at > created_at
```

Constraint name:

```text
ck_invitations_expires_after_created_at
```

### Accepted-State Consistency

The database enforces that accepted invitations contain an accepted user and timestamp and do not contain revocation state.

Constraint name:

```text
ck_invitations_accepted_state
```

### Revoked-State Consistency

The database enforces that revoked invitations contain a revocation timestamp and do not contain acceptance state.

Constraint name:

```text
ck_invitations_revoked_state
```

## Invitation Issuance

The issuance service accepts:

```text
IssueInvitationCommand
- tenant_id
- issuer_user_id
- invited_email
- role
```

It returns:

```text
IssuedInvitation
- id
- tenant_id
- invited_email
- role
- expires_at
- token
```

The token in this result is a one-time sensitive value intended for a future delivery boundary.

### Authorization Rules

The issuer must have:

```text
active membership
same tenant
role owner or admin
```

The requested invitation role must be:

```text
admin or staff
```

A staff member cannot issue invitations.

### Existing Membership Protection

Before issuing an invitation, the service resolves the global user associated with the canonical invited email.

If that user already has any membership in the tenant, issuance is rejected.

```text
Active membership
    -> user is already a tenant member

Disabled membership
    -> requires an explicit reactivation workflow
```

Invitation issuance must not bypass membership lifecycle state.

### Issuance Flow

```text
Validate requested role
        |
        v
Canonicalize invited email
        |
        v
Lock tenant
        |
        v
Require active tenant
        |
        v
Lock issuer membership
        |
        v
Require active owner or admin
        |
        v
Reject existing membership
        |
        v
Read current time
        |
        v
Lock pending invitation for tenant and email
        |
        +-----------------------------+
        |                             |
        | still valid                 | effectively expired
        v                             v
AlreadyPendingError              mark expired
                                      |
                                      v
                                 flush state
        |
        v
Generate bearer token
        |
        v
Persist only digest
        |
        v
Create pending invitation
        |
        v
Flush without commit
```

The initial validity window is:

```text
7 days
```

The clock and token factory are injectable for deterministic testing.

## Invitation Acceptance

The acceptance service accepts:

```text
AcceptInvitationCommand
- token
- password: optional
```

It returns:

```text
AcceptedInvitation
- invitation_id
- tenant_id
- membership_id
- user_id
- role
- user_was_created
- accepted_at
```

The caller cannot provide a `user_id`.

The invited email determines which global user may receive the membership.

### Token Resolution and Locking

The service first hashes the supplied token and performs a non-locking lookup by digest to discover:

```text
invitation_id
tenant_id
```

It then locks:

```text
Tenant
    |
    v
Invitation
```

The invitation is re-read under `FOR UPDATE`.

### Refreshing Locked State

SQLAlchemy maintains one in-memory object instance per database identity inside a Session.

Because the acceptance flow performs an initial non-locking read and later re-reads the same invitation under `FOR UPDATE`, the ORM identity map may otherwise reuse the earlier object state.

The locked query therefore uses:

```text
populate_existing = true
```

This forces the row returned after lock acquisition to refresh the existing ORM instance from PostgreSQL.

Without this refresh, a transaction that waited for another acceptance or revocation could acquire the row lock but continue evaluating stale invitation state already stored in its Session.

The combination provides the required behavior:

```text
FOR UPDATE
    -> serializes competing lifecycle transitions

populate_existing
    -> refreshes the ORM object after waiting for the lock
```

This is essential for correct replay and acceptance-versus-revocation handling.

### Existing User Acceptance

When the canonical invited email belongs to an existing global user:

```text
Lock global user by email
        |
        v
Require active user
        |
        v
Create tenant membership
```

No password is required because credential verification belongs to a future authenticated delivery or API boundary.

The domain service still guarantees that the membership can only be created for the user whose canonical email matches the invitation.

### New User Acceptance

When the invited email does not belong to a global user:

```text
Require password
        |
        v
Create global user
        |
        v
Create password credential
        |
        v
Create tenant membership
```

The existing identity creation service is reused, preserving:

- canonical email handling;
- password policy;
- Argon2id hashing;
- global email uniqueness handling.

### Acceptance Flow

```text
Digest supplied token
        |
        v
Resolve invitation metadata
        |
        v
Lock tenant
        |
        v
Re-read and lock invitation
        |
        v
Refresh ORM state from PostgreSQL
        |
        v
Validate lifecycle state
        |
        v
Validate effective expiration
        |
        v
Require active tenant
        |
        v
Lock global user by invited email
        |
        +-----------------------------+
        |                             |
        | existing user               | no user
        v                             v
Require active user             Require password
        |                             |
        |                        Create global user
        |                        and credential
        +-------------+---------------+
                      |
                      v
Reject existing membership
                      |
                      v
Create active membership
                      |
                      v
Mark invitation accepted
                      |
                      v
Set accepted user and timestamp
                      |
                      v
Flush without commit
```

## Invitation Revocation

The revocation service accepts:

```text
RevokeInvitationCommand
- tenant_id
- invitation_id
- actor_user_id
```

It returns:

```text
RevokedInvitation
- invitation_id
- tenant_id
- revoked_at
```

### Authorization Rules

The actor must have:

```text
active membership
same tenant
role owner or admin
```

### Tenant Isolation

The invitation lookup requires both:

```text
invitation_id
tenant_id
```

An invitation belonging to another tenant is treated as unavailable within the current tenant boundary.

### Revocation Flow

```text
Lock tenant
        |
        v
Require active tenant
        |
        v
Lock actor membership
        |
        v
Require active owner or admin
        |
        v
Lock invitation within tenant
        |
        v
Require pending state
        |
        v
Validate effective expiration
        |
        v
Set status to revoked
        |
        v
Set revoked_at
        |
        v
Flush without commit
```

Accepted, revoked, and expired invitations cannot transition back to pending.

## Concurrency Model

Invitation lifecycle workflows use PostgreSQL row locks and database constraints rather than in-process locks.

This keeps correctness valid across:

- multiple API processes;
- worker processes;
- multiple application instances;
- concurrent database sessions.

### Concurrent Issuance

Issuance locks the tenant row before evaluating pending invitations.

Two concurrent issuance attempts for the same tenant and email produce:

```text
one pending invitation
one already-pending failure
```

The partial unique index remains the final database backstop if application locking is bypassed.

### Concurrent Acceptance

Two concurrent acceptance attempts for the same token produce:

```text
one accepted invitation
one membership
one replay rejection
```

The second transaction waits for the lifecycle lock and then refreshes the invitation state before evaluating it.

### Acceptance Versus Revocation

Acceptance and revocation may compete for the same pending invitation.

Exactly one terminal transition may succeed:

```text
Acceptance wins
    -> invitation = accepted
    -> membership exists
    -> revocation observes accepted state

Revocation wins
    -> invitation = revoked
    -> membership does not exist
    -> acceptance observes revoked state
```

The system must never persist:

```text
accepted and revoked state together
accepted invitation without membership
revoked invitation with accepted user
multiple memberships from one invitation
```

### Direct Database Concurrency

Automated integration coverage also bypasses application services and inserts concurrent pending invitations directly.

PostgreSQL allows one row and rejects the other through:

```text
uq_invitations_one_pending_per_tenant_email
```

This verifies that the database remains the final authority for the pending-invitation invariant.

## Lock Ordering

The workflows use stable lock ordering.

Issuance:

```text
Tenant
    |
    v
Issuer Membership
    |
    v
Pending Invitation
```

Acceptance:

```text
Tenant
    |
    v
Invitation
    |
    v
Global User
    |
    v
Membership lookup or creation
```

Revocation:

```text
Tenant
    |
    v
Actor Membership
    |
    v
Invitation
```

The tenant row acts as the initial serialization boundary for invitation lifecycle changes within one tenant.

Operations against unrelated tenants may proceed independently.

## Transaction Ownership

Invitation services call:

```text
flush()
```

but do not call:

```text
commit()
```

This allows future application workflows to compose operations atomically:

```text
Accept Invitation
Create Membership
Write Audit Event
Schedule Welcome Delivery
Commit
```

The caller owns the final transaction decision.

Rollback coverage verifies:

- issued invitations disappear when the caller rolls back;
- accepted invitation state and membership creation roll back together;
- newly created user and password credential roll back with failed acceptance;
- revoked invitation state rolls back when the caller does not commit.

## Failure Model

Expected invitation failures include:

```text
InvitationNotFoundError
InvitationAlreadyPendingError
InvitationRoleNotAllowedError
InvitationIssuerNotAuthorizedError
InvitationActorNotAuthorizedError
InvitationMembershipAlreadyExistsError
InvitationTokenInvalidError
InvitationExpiredError
InvitationRevokedError
InvitationAlreadyAcceptedError
InvitationPasswordRequiredError
```

Related identity and tenancy failures may propagate:

```text
InvalidEmailError
PasswordPolicyViolationError
EmailAlreadyRegisteredError
UserDisabledError
TenantNotFoundError
TenantDisabledError
```

These exceptions:

- do not import FastAPI;
- do not contain HTTP status codes;
- do not expose plaintext tokens;
- do not expose token digests;
- do not expose persistence internals.

A future API boundary will map application failures to transport-specific responses.

## Security Boundaries

The model establishes these rules:

- invitation tokens are bearer secrets;
- plaintext tokens are never persisted;
- plaintext tokens and digests must not be logged;
- invitation roles cannot grant ownership;
- only active owners and admins may issue invitations;
- only active owners and admins may revoke invitations;
- staff members cannot manage invitations;
- a membership from another tenant provides no authority;
- an invitation from another tenant is not visible within the current tenant context;
- the invited email determines the target global user;
- callers cannot substitute another user identifier;
- disabled global users cannot accept invitations;
- disabled memberships require reactivation rather than reinvitation;
- accepted invitations cannot be replayed;
- revoked invitations cannot be accepted;
- effective expiration is checked at operation time;
- database constraints remain the final concurrency authority.

## Indexing and Scaling

The invitation model includes:

```text
UNIQUE token_digest
PARTIAL UNIQUE tenant_id + invited_email for pending invitations
INDEX tenant_id + status
INDEX invited_email
```

These indexes support:

- token resolution;
- tenant invitation listing;
- pending invitation lookup;
- invited-email lookup;
- database invariant enforcement.

The current tenant-level serialization strategy is intentionally simple and reliable for the expected workload.

Consequences:

```text
Different tenants
    -> invitation lifecycle changes proceed independently

Same tenant
    -> invitation lifecycle changes may serialize
```

If tenant-level invitation throughput becomes significant, locking may evolve toward a narrower boundary such as invitation rows or a tenant-and-email advisory lock.

Caching is intentionally deferred because invitation lifecycle and token validity are consistency-sensitive security data.

## Intentionally Deferred

The following capabilities are intentionally deferred:

- invitation HTTP endpoints;
- authenticated acceptance transport;
- email provider integration;
- email templates;
- delivery retries;
- reminder emails;
- background expiration cleanup;
- invitation listing APIs;
- bulk invitations;
- resend operations;
- configurable expiration per tenant;
- invitation audit logs;
- membership reactivation;
- post-onboarding role changes;
- tenant permission middleware;
- owner invitations;
- ownership transfer through invitations;
- invitation caching.

Email delivery is intentionally separated from the domain lifecycle. The issuance service produces the one-time token, while a future delivery boundary will decide how the invitation is communicated and retried.
